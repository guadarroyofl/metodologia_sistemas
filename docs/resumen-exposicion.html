01 Qué es

Cada prenda es una pieza física única: no hay cantidades, hay estado (disponible, reservada, vendida, archivada). El sistema cubre catálogo, venta, control de stock, rentabilidad y reportería.

06 Seguridad

  • Contraseñas: PBKDF2-HMAC-SHA256, 260.000 iteraciones, sal aleatoria y comparación en tiempo constante.
  • JWT + RBAC: token firmado con expiración; require_admin en endpoints y servicios sensibles.
  • DTOs separados: el público nunca recibe costo ni margen; solo el schema admin.
  • Uploads: MIME, tamaño, decodificación real con Pillow, reencodeo y nombre UUID.

07 Buenas prácticas aplicadas

  • Separación de responsabilidades e inyección de dependencias.
  • Tres niveles de validación: Pydantic → servicio → constraints SQL.
  • Errores uniformes con excepciones de dominio y handlers globales.
  • Transacciones atómicas en checkout y cancelación.
  • Doble venta imposible: UPDATE condicionado + control de filas.
  • Baja lógica para no romper historial ni claves foráneas.
  • Configuración por entorno y seed idempotente.
  • Pruebas de integración con base temporal aislada + CI en cada push.

08 Trade-offs asumidos

  • SQLite: cero configuración; escrituras concurrentes limitadas.
  • JWT en localStorage: simple; menos seguro que cookie httpOnly.
  • IA determinística: auditable y sin costo; menos flexible que un LLM.

Lámina 1 · Arquitectura

Cómo se conecta el sistema

Lámina 2 · Flujo

Qué pasa cuando se edita un precio

Petición real
UI Formulario admin Envía PATCH /api/products/12 con { price }
Controller Valida y autoriza Schema ProductUpdate + require_admin decodifica el JWT
Service Aplica la regla Precio > costo, recálculo de margen, actualización de estilos
Repository Persiste SQLAlchemy actualiza la fila dentro de la transacción
DB Commit Constraint price > 0 · si falla, rollback y 409
UI Respuesta AdminProductOut y la tabla se refresca

Checkout atómico (sin doble venta)

  1. Se valida que todas las prendas estén available.
  2. Se ejecuta un UPDATE products SET status='sold' WHERE id=? AND status='available'.
  3. Si rowcount != 1, otra persona compró primero: 409 y rollback.
  4. Se insertan sales, sale_items y inventory_movements en la misma transacción.
  5. Commit único: o se guarda todo, o no se guarda nada.

Subida de fotos (multipart)

  1. POST /api/uploads/image, solo administrador.
  2. Se valida MIME y tamaño máximo de 8 MB.
  3. Pillow decodifica: si no es imagen real, 422.
  4. Se reorienta por EXIF, se limita a 1600 px y se reencodea a WEBP.
  5. Se guarda con nombre UUID en backend/uploads/ y se sirve en /media/....

Lámina 3 · Datos

Modelo entidad-relación

10 tablas en tercera forma normal, claves foráneas activas y reglas de borrado explícitas. Las tablas password_reset_tokens y price_suggestions se detallan aparte para no saturar el diagrama.

3FN

Integridad y reglas

  • FK activas (PRAGMA foreign_keys=ON) y modo WAL.
  • RESTRICT en categorías con prendas y en ventas con comprador.
  • CASCADE en sale_items y en la tabla puente.
  • SET NULL en vendedor y referencias opcionales.
  • CHECK (price > 0), CHECK (quantity = 1), UNIQUE (sale_id, product_id).

Normalización

  • Sin grupos repetidos: el detalle de venta va en sale_items.
  • Sin dependencias parciales: la tabla puente resuelve el N:M.
  • Sin dependencias transitivas: categoría y estilo se referencian por ID.
  • Los snapshots de precio y costo son históricos, no duplicación de estado actual.

Fuera del diagrama

  • password_reset_tokens: 1:N con users, guarda solo el hash SHA-256.
  • price_suggestions: 1:N con users y 0..1:N con products; audita cada evaluación de IA.
